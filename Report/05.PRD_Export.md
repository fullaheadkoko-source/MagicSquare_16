## 1. 제품 개요

### 1.1 문제 정의(요약)
- 본 제품은 \(4 \times 4\) 격자에서 **합의된 값 집합과 규칙**(불변식)을 만족하는 **완성된 배치**를 산출하거나, 그러한 배치의 **존재 여부를 판정**하는 문제를 다룬다.
- “마방진을 만든다”가 아니라, **입력/출력 계약**과 **검증 가능한 불변식**을 먼저 고정하고, 이를 **TDD**로 보호하는 학습용 시스템이다.

### 1.2 목적(학습 목적)
- **Invariant 중심 설계 사고** 훈련(“항상 참이어야 하는 것”을 규칙으로 고정)
- **Dual-Track TDD** 훈련(UI 계약 테스트와 Domain 규칙 테스트를 병렬로 RED→GREEN→REFACTOR)
- **입력/출력 계약 명확화** 훈련(검증 가능하고 회귀 방지되는 스펙)
- **Clean Architecture(ECB)** 레이어 분리 훈련(의존성 방향 준수)

## 4. Dual-Track TDD · Contract · MLOps 정렬

### 4.1 Dual-Track 원리
- **UI Track (boundary)**: 디자인·표현이 아니라 **UX Contract**(사용자에게 약속한 가시 상태·문구·응답 형태)로 RED를 만든다.
- **Logic Track (control + entity)**: **Logic Rule**(허용/거부/반환/계산)로 RED를 만든다.
- **GREEN·REFACTOR**는 두 트랙 모두에서 동일하게 진행하되, 테스트 범위는 분리한다.
- **독립성(필수)**: UI 테스트는 도메인 알고리즘·엔티티 내부 구조에 의존하지 않는다. Logic 테스트는 UI 프레임워크·화면 표현을 알지 않는다.

### 4.2 UX Contract 언어(boundary 테스트 설계)
- 보인다 / 안 보인다(예: 표준 `message` 텍스트, 성공 요약)
- 가능하다 / 불가능하다(예: 제출·재시도 — 구현 시 적용)
- 활성화 / 비활성화
- 포함한다 / 포함하지 않는다(예: 응답 JSON에 특정 `code` 존재)

### 4.3 Logic Rule 언어(control/entity 테스트 설계)
- 허용한다 / 거부한다(입력 전제, 스키마)
- 유지한다 / 중단한다(파이프라인 단계)
- 반환한다 / 차단한다(성공 배열 vs 실패)
- 계산한다 / 저장한다(마방진 판정·좌표; 행렬 저장은 선택 데이터층)

### 4.4 UX Contract ↔ Logic Rule 매핑(요약)

| 시나리오(요약) | UX Contract(boundary) | Logic Rule(control+entity) |
|---|---|---|
| 행렬이 4×4가 아님 | 표준 `message` `Matrix must be 4x4.` 가 응답·화면 계약에 **포함**된다 | Shape 검증이 **거부** → `UI_INVALID_SHAPE` |
| 빈칸(0)이 2개가 아님 | `Matrix must contain exactly 2 empty cells (0).` **포함** | EmptyCount 검증이 **거부** → `UI_INVALID_EMPTY_COUNT` |
| 셀이 0 또는 1..16이 아님 | `Cell values must be 0 or 1..16.` **포함** | Range 검증이 **거부** → `UI_OUT_OF_RANGE` |
| 0 제외 중복 | `Non-zero values must be unique.` **포함** | 중복 검증이 **거부** → `UI_DUPLICATE_NON_ZERO` |
| 두 배정 모두 비마방진 | `No magic square completion exists for this input.` **포함** | 조합 시도 후 **차단** → `UI_UNSOLVABLE` |
| 유효 입력·해 존재 | 성공 표현은 구현 자유, **계약상** 길이 6·1-index·`n1,n2` 순서 규칙 충족이 **보장**된다 | 기본/반대 배정 규칙에 따라 **해를 반환**한다 |
| (선택) 저장/로드 실패 | `Failed to persist or load the matrix.` **포함** | I/O **실패** → `UI_DATA_ERROR` |

**테스트로 옮길 To-Do**: 위 표에서 **허용/거부/반환/차단/계산** 등 **판단(Decision)**이 있는 행만 1급 테스트 대상으로 한다. 순수 정리 작업만 있는 할 일은 테스트로 변환하지 않는다.

### 4.5 MLOps 관점 정렬(본 PRD에의 적용)

본 제품은 ML 모델 학습·배포가 스코프 핵심은 아니나, MLOps에서 쓰는 **계약·게이트·재현성** 사고를 그대로 적용한다.

| 출력·서빙 계약 | §5.2 성공 출력 스키마 |
| 실패·API 계약 | §5.3 에러 코드·문구·우선순위 |
| 재현성·결정성 | §2.1, §7.1 |
| 품질 게이트 | §7.2 커버리지 목표 |

## 5. 스코프(기능 요구사항)

### 5.1 입력 계약(Input schema) — 고정
- 입력은 **정수 4x4 행렬**이다.
- 셀 값은 **0 또는 1..16**만 허용한다.
- **0은 빈칸**을 의미한다.
- **0은 정확히 2개**여야 한다.
- **0을 제외한 값은 중복이 없어야 한다.**

### 5.2 출력 계약(Output schema) — 고정(성공 시)
- 성공 결과는 **길이 6의 정수 배열**이다.
- 포맷: `[r1, c1, n1, r2, c2, n2]`
  - `r1,c1,r2,c2`: **1-index 좌표**(1..4)
  - `n1,n2`: 입력에서 누락된 두 숫자
- 빈칸 좌표 순서:
  - **행 우선(row-major), 열 증가**로 스캔하여 발견된 0의 좌표를 `(firstEmpty, secondEmpty)`로 고정한다.
- `n1,n2` 순서 규칙(결정적 출력 정책):
  - **기본 배정**: `firstEmpty=smallMissing`, `secondEmpty=largeMissing`
  - 기본 배정이 마방진이면 그 순서로 반환
  - 기본 배정이 마방진이 아니고, **반대 배정**이 마방진이면 반대 순서로 반환
  - 둘 다 아니면 실패(해 없음)

### 5.3 에러 계약(Error schema) — 고정(실패 시)
- 실패 결과는 `error` 객체로 반환한다.
  - `code`: 표준 코드(아래 중 하나)
  - `message`: 표준 문구(아래 문자열과 **완전 일치**)
  - `details`: 선택(테스트 가능한 고정 필드만 허용)

#### 표준 에러 코드/문구(정확히 일치)
| code | message (정확히 일치) | 발생 조건 |
|---|---|---|
| `UI_INVALID_SHAPE` | `Matrix must be 4x4.` | 입력이 4x4가 아님 |
| `UI_INVALID_EMPTY_COUNT` | `Matrix must contain exactly 2 empty cells (0).` | 0의 개수가 2개가 아님 |
| `UI_OUT_OF_RANGE` | `Cell values must be 0 or 1..16.` | 값이 0 또는 1..16 범위를 벗어남 |
| `UI_DUPLICATE_NON_ZERO` | `Non-zero values must be unique.` | 0을 제외한 중복 존재 |
| `UI_UNSOLVABLE` | `No magic square completion exists for this input.` | 두 배정 모두 마방진 실패 |
| `UI_DATA_ERROR` | `Failed to persist or load the matrix.` | (선택) 저장/로드 실패 |

#### 에러 반환 규칙(회귀 보호)
- 실패 시 **첫 위반 1개만** 반환한다(에러 리스트 금지).
- 에러 우선순위는 아래 순서를 고정한다.
  - **Shape → EmptyCount → Range → Duplicate → Unsolvable → Data**
- **I-05(누락 정확히 2개)** 는 I-02·I-03·I-04를 만족하면 **항상 도출**되는 논리적 결과이므로, 별도 `code`/`message`는 두지 않는다(우선순위 단계에도 넣지 않는다).

## 6. 도메인 불변식(Invariants)

### 6.1 입력 계약 불변식(Preconditions)
- **I-01 (Shape)**: 입력은 정확히 4x4
- **I-02 (EmptyCount)**: 0은 정확히 2개
- **I-03 (Range)**: 각 값은 0 또는 1..16
- **I-04 (UniqNonZero)**: 0 제외 중복 없음
- **I-05 (MissingExactly2)**: 1..16 중 누락 값은 정확히 2개 — I-02~I-04 만족 시 **자동 성립**(별도 에러 단계 없음)

### 6.2 마방진 규칙 불변식(Domain Rules)
- **I-06 (MagicConstant)**: 값 집합이 1..16인 완성 상태에서 마방진 상수는 **34**
  - 근거: \( \sum_{k=1}^{16} k = 136 \), \(136/4 = 34\)
- **I-07 (RowSum)**: 모든 행 합 동일(완성 상태에서는 34)
- **I-08 (ColSum)**: 모든 열 합 동일(완성 상태에서는 34)
- **I-09 (DiagSum)**: 두 대각선 합 동일(완성 상태에서는 34)
- **I-10 (DeterministicOrderRule)**: §5.2의 `n1,n2` 출력 순서 규칙은 항상 결정적이어야 함

## 9. 사용자 스토리(요약) 및 승인 기준(AC)

각 스토리는 **UI Track**(boundary·UX Contract)과 **Logic Track**(control+entity)으로 AC를 구분한다. 구현 없이도 테스트 제목·관심사 분리에 쓴다.

### 9.1 Story 1 — 입력 검증
- **Logic Track AC**
  - 4x4가 아니면 검증이 **거부**한다.
  - 빈칸(0) 2개가 아니면 **거부**한다.
  - 0 제외 중복이 있으면 **거부**한다.
  - 값 범위(0 또는 1..16) 위반 시 **거부**한다.
- **UI Track AC**
  - 위 각 실패에 대해 §5.3 표의 **해당 `message`가 사용자 계약(응답/화면)에 포함**된다.
  - **첫 위반 1개만** 노출·반환된다(우선순위 §5.3).

### 9.2 Story 2 — 빈칸 탐색
- **Logic Track AC**: row-major 순서 유지; 정확히 2개 좌표 산출.
- **UI Track AC**: (직접 노출 시) 좌표 표시가 Logic이 산출한 순서와 **일치**; API만일 경우 생략 가능.

### 9.3 Story 3 — 누락 숫자 탐색
- **Logic Track AC**: 1..16 중 누락 2개; 오름차순(small, large)으로 내부 사용.
- **UI Track AC**: 해당 없음(출력은 §5.2 최종 배열에만 반영).

### 9.4 Story 4 — 마방진 판정
- **Logic Track AC**: 모든 행·열·두 대각선 합이 완성 규칙과 **일치**하는지 **계산·판정**한다.
- **UI Track AC**: 해당 없음(판정 결과는 Story 5·boundary로 전달).

### 9.5 Story 5 — 두 조합 시도(완성/출력)
- **Logic Track AC**: small→firstEmpty / large→secondEmpty 먼저 시도; 실패 시 reverse; 성공 시 길이 6·1-index; 둘 다 실패 시 `UI_UNSOLVABLE`로 **실패 구성**.
- **UI Track AC**: 성공 시 계약된 배열 형태 **포함**; `UI_UNSOLVABLE` 시 표준 `message` **포함**.

## 11. 가정 / 리스크

### 11.1 가정(Assumptions)
- 값 집합은 **1..16**이며, 빈칸은 **정확히 2개(0)** 이다.
- 해결 전략은 “두 빈칸에 두 숫자 배정”의 **2가지 조합 시도**로 충분하다(본 스코프).

### 11.2 리스크(Risks)
- 스펙의 핵심(에러 문구, 출력 포맷)이 변경되면 테스트가 대규모로 깨질 수 있다(의도된 회귀 보호).
- 입력 계약 위반 처리에서 “우선순위”가 흔들리면 외부 계약이 불안정해진다(반드시 테스트로 고정).

## 권장 방향(실무에서 많이 쓰는 패턴)

**같은 기능 브랜치에서 RED → GREEN을 이어가고, GREEN이 끝난 뒤 한 번에 PR/머지**하는 방식이 TDD 흐름과도 맞습니다.

- RED 커밋이 이미 있다면: **현재 브랜치 그대로** 최소 구현만 추가해 테스트를 하나씩 녹색으로 만듭니다.
- PR 제목/설명에 “RED + GREEN” 또는 “TDD: failing tests then implementation”처럼 적어 두면 리뷰어가 범위를 이해하기 쉽습니다.
- `.cursorrules`의 green 규칙(최소 구현, 리팩터는 나중)과도 잘 맞습니다.

즉, **“RED만 먼저 머지”를 꼭 할 필요는 없고**, 미머지 상태라면 **지금 브랜치 = `feature/...` 하나로 RED→GREEN까지 가져가도 됩니다.**

## 대안(팀이 RED만 main에 두고 싶을 때)

- **RED를 먼저 머지**한 다음, `main`(또는 `develop`)에서 **`feature/dual-track-green`** 같은 브랜치를 새로 파서 구현만 올립니다.
- 장점: PR가 “테스트 추가”와 “구현”으로 나뉘어 리뷰가 쉬울 수 있음.  
- 단점: RED만 먼저 올리면 CI가 잠깐 빨간색일 수 있음(팀 정책에 따라 비추일 수 있음).

## Dual-Track(UI / Logic)과 브랜치

트랙을 **브랜치까지 쪼개지 않아도** 됩니다. 한 브랜치 안에서:

- 커밋을 `test:`(RED) / `feat:` 또는 `fix:`(GREEN)처럼 나누거나,
- PR을 나중에 쪼개고 싶다면 **커밋 단위만** 트랙별로 정리해 두면 `git cherry-pick`으로 분리하기도 수월합니다.

**정리**: 지금 머지 안 했다면 **현재 브랜치에서 GREEN까지 진행 → 전부 통과 후 머지**를 기본으로 추천합니다. 팀이 “RED PR과 구현 PR을 반드시 분리”한다는 규칙이 있을 때만, RED 머지 후 `main`에서 GREEN 전용 브랜치를 파는 쪽을 쓰면 됩니다.

```17:28:c:\DEV\MagicSquare_16\boundary\ui_shape.py
def validate_4x4_shape(matrix: list[list[int]]) -> None:
    """Reject inputs that are not exactly 4×4.

    Args:
        matrix: Candidate puzzle grid.

    Raises:
        UIBoundaryError: With ``UI_INVALID_SHAPE`` and PRD message if not 4×4.
    """
    if len(matrix) != 4:
        raise UIBoundaryError("UI_INVALID_SHAPE", "Matrix must be 4x4.")
    for row in matrix:
        if len(row) != 4:
            raise UIBoundaryError("UI_INVALID_SHAPE", "Matrix must be 4x4.")
```

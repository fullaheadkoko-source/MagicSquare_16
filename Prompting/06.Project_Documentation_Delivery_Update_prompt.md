## PRD에 자주 넣는 내용(일반 프레임)

| 영역 | 설명 |
|------|------|
| **제품 개요** | 무엇을 만들지, 왜 만드는지(문제·기회) |
| **목표 / 비목표** | 하겠다는 것과 일부러 하지 않을 것 |
| **사용자·시나리오** | 누가 쓰는지, 주요 사용 흐름 |
| **기능 요구사항** | 입력·출력·상태·에러 등 **동작을 문장/스키마로 고정** |
| **도메인 규칙** | 불변식, 수식, 판정 기준(마방진이면 합 34 등) |
| **비기능 요구사항** | 성능, 보안, 결정성, 접근성, 품질 목표 |
| **아키텍처·제약** | 레이어, 의존성, 기술 스택(필요 시) |
| **스토리·승인 기준** | 사용자 스토리 + Given/When/Then 또는 체크리스트형 AC |
| **검증·릴리스** | 테스트 계획, 트레이서빌리티, 출시 기준(선택) |
| **가정·리스크** | 전제, 알려진 한계, 변경 시 영향 |

제품이 **B2B·대규모**이면 메트릭(KPI), 로드맵(MVP vs 이후), 이해관계자, 용어집 등을 더 붙이기도 합니다.

## 지금 `PRD.md`에 이미 있는 것

- **1** 제품 개요(문제, 학습 목적)  
- **2** 목표 / 비목표  
- **3** 페르소나·여정

- **7** ECB 아키텍처 요구  
- **8** 스토리 + AC

- **10** 가정·리스크  

즉, **“구현 전에 고정해야 할 것” 중심 PRD**로는 구성이 잘 되어 있습니다.

## 보강하고 싶다면 넣을 수 있는 것(선택)

- **용어**: “빈칸”, “배정”, “기본/반대 배정” 등 한 페이지짜리 용어 정의  
- **예시**: 유효 입력 1~2개와 기대 출력·에러 JSON/배열 예시(문서만, 코드와 동일하게)  
- **MVP 범위**: “첫 릴리스에는 CLI만” 같은 **출력 채널** 고정  
- **완료 정의(DoD)**: PR 머지 조건(테스트 통과, 린트 등)이 팀 규칙과 맞다면 한 줄이라도  
- **버전/변경**: “스펙 v1”과 변경 시 프로세스(의도적으로 엄격한 회귀 전략과 맞춤)

정리하면, **PRD에 들어갈 내용**은 위 표가 기준이고, **이 프로젝트용으로는** 지금 문서가 그 기준을 이미 잘 반영하고 있습니다. 추가는 “팀/리뷰어가 헷갈릴 만한 부분”만 골라 보강하면 됩니다.

**Cursor**

Dual-Track TDD와 MLOps를 같이 쓰는 방향은 **잘 맞습니다**. 다만 MLOps 쪽은 “순수 로직”보다 **데이터·모델·환경**이 끼어들어서, 슬라이드의 **UX Contract / Logic Rule 분리**와 **판단(Decision)만 테스트로**라는 원칙을 그대로 옮기되 **Logic 트랙을 넓게 정의**하는 게 핵심입니다.

---

### 왜 잘 맞는지

- **UI 트랙**: 추론 UI, 대시보드, 알림, “로딩/실패/설명 가능” 같은 **경계(boundary)**는 지금 슬라이드처럼 **보인다/안 보인다, 가능/불가** 같은 UX Contract로 RED를 잡기 좋습니다. UI 테스트는 **요청 포맷·표시 문구·상태 전이**만 알면 됩니다.
- **Logic 트랙**: MLOps에서의 “로직”은 한 덩어리가 아니라 **여러 층**으로 나누는 게 맞습니다.  
  - **도메인/정책**: 스키마 검증, 임계값, 라우팅, AB 할당 규칙  
  - **모델 계약**: 입력 스키마, 출력 스키마, 차원, 허용 라벨 집합  
  - **파이프라인**: 재현 가능한 전처리, 아티팩트 버전, 승인 게이트  
  이런 것들은 pytest(또는 계약 테스트)로 **규칙 기반 RED**를 만들기 좋습니다.

슬라이드의 **“UI는 로직을 모르고, 로직은 UI를 모른다”**는 MLOps에서도 그대로 유효합니다. UI는 “예측 결과 JSON의 필드” 수준만 알고, 학습 코드는 Streamlit을 몰라도 됩니다.

---

### MLOps에서만 조심할 점

1. **비결정성**  
   같은 입력이라도 시드·GPU·버전에 따라 미세하게 달라질 수 있습니다. “완전 동일 출력” 대신 **스키마·범위·후처리 불변식·골든셋 메트릭 하한** 같은 **검증 가능한 계약**으로 Logic RED를 잡는 편이 현실적입니다.

2. **Logic 트랙을 “모델 파일” 하나로만 두지 않기**  
   학습/배포 파이프라인은 **데이터 검증 → 학습 → 평가 → 레지스트리 → 서빙**으로 나누고, 각 단계에 **허용/거부, 반환/차단** 같은 동사로 끝나는 Decision을 PRD·테스트에 박아 두면 슬라이드의 “3단 매핑”과 잘 맞습니다.

3. **UX ↔ Logic 매핑**  
   예: “모델 버전 불일치” → UX에서는 **특정 에러 문구/배너가 보인다**, Logic에서는 **요청이 거부된다**처럼 한 행에 두 열을 맞추면 PRD와 회귀 테스트가 같이 굳어집니다.

4. **“판단이 있는 것만 테스트”**  
   MLOps에서는 “노트북 정리하기” 같은 할 일과, “스키마 위반이면 차단한다” 같은 할 일을 구분하는 게 특히 중요합니다. 후자만 테스트·CI 대상으로 두면 부담이 줄고 효과는 큽니다.

---

### 짧은 결론

**Dual-Track UI + Logic TDD를 MLOps에 적용하는 것은 좋은 조합**이고, PRD에는 지금 MagicSquare PRD처럼 **입출력·에러 계약**에 더해 **UX Contract ↔ Logic Rule 매핑 표**와 **파이프라인 단계별 Decision**만 명시해 두면 슬라이드 방법론과 MLOps가 잘 이어집니다.  
원하시면 `docs/PRD.md`에 넣을 **MLOps용 섹션 목차(한 페이지 분량)**만 짧게 초안으로 적어 드리겠습니다.

# PRD 재구성 — Dual-Track UI + Logic TDD · MLOps 정렬

**메타**  
- 프로젝트: MagicSquare — 4×4, 빈칸 2개(0), Python 3.10+  
- 핵심 방법: **UI는 디자인(UX Contract)으로 RED**, **로직은 규칙(Logic Rule)으로 RED** — GREEN·REFACTOR는 공통.  
- **두 트랙은 독립**: UI 테스트는 도메인 구현 세부를 모르고, Logic 테스트는 UI를 모른다.

---

## 1. 제품 한 줄 · 목적

| 구분 | 내용 |
|------|------|
| **문제** | 4×4 격자에서 합의된 값 집합·규칙(불변식)을 만족하는 완성 배치를 산출하거나, 존재 여부를 판정한다. |
| **접근** | “마방진 구현”이 아니라 **입출력 계약 + 검증 가능한 불변식**을 먼저 고정하고 TDD로 보호하는 학습용 시스템. |
| **학습 목적** | Invariant 중심 설계, Dual-Track TDD, 계약 명확화, Clean ECB. |

**목표 / 비목표**는 기존과 동일: ECB, TDD-first, 결정적·재현 가능 동작 / 비목표: 과한 스타일링, 선제 성능 최적화, 모든 해 열거.

---

## 2. Dual-Track — 역할 분리

### 2.1 UI Track (Boundary)

**검증 대상**: 파싱·표시·에러 매핑·“사용자가 보는 상태”가 **계약과 일치**하는지.

**UX Contract 언어(요약)** — PRD에 대응시키면:

- 특정 **에러 메시지(표준 문구)** 가 보인다 / 보이지 않는다.  
- **성공 시** 길이 6 배열·요약 UI가 **일관되게** 보인다(표현은 구현 선택, **계약 필드**는 고정).  
- **제출/실행** 가능·불가능(입력 미완성 등은 구현 정책이면 PRD 밖 — 단, **boundary가 반환하는 API 계약**은 고정).

**경계에서 고정하는 것**(기존 §4.3, §7 boundary):

- 실패 시 `error`: `code`, `message`(문자열 **완전 일치**), 선택 `details`.  
- **첫 위반 1개만**, 우선순위: Shape → EmptyCount → Range → Duplicate → (MissingNotTwo) → Unsolvable → Data.  
- 표준 코드·문구 테이블( `UI_INVALID_SHAPE` … `UI_DATA_ERROR` ).

### 2.2 Logic Track (Control + Entity)

**검증 대상**: 스키마·탐색·판정·배정 순서 — **UI 없이** pytest 등으로 충분한가.

**Logic Rule 언어(요약)**:

- **거부한다 / 허용한다**: 입력 전제(I-01 … I-05).  
- **계산한다**: 빈칸 row-major, 누락 두 수, 행·열·대각 합 34 판정.  
- **반환한다 / 차단한다**: 성공 시 `[r1,c1,n1,r2,c2,n2]`; 실패 시 unsolvable 등.  
- **유지한다**: 결정적 `n1,n2` 순서(I-10).

**엔티티·컨트롤 불변식**: 기존 §5 (I-01 … I-10), §4.1–4.2 입력·출력 스키마.

---

## 3. UX Contract ↔ Logic Rule 매핑 표

(슬라이드의 “3단 매핑”에 해당 — **판단(Decision)이 있는 행**만 테스트 1급 대상으로 두면 됨.)

| 시나리오(요약) | UX Contract (Boundary) | Logic Rule (Control+Entity) |
|----------------|-------------------------|------------------------------|
| 행렬이 4×4가 아님 | 표준 메시지 `Matrix must be 4x4.` 가 사용자/응답에 **포함**된다 | Shape 검증이 **거부**한다 (`UI_INVALID_SHAPE`) |
| 빈칸(0)이 2개가 아님 | `Matrix must contain exactly 2 empty cells (0).` **포함** | EmptyCount 검증이 **거부**한다 |
| 셀이 0 또는 1..16이 아님 | `Cell values must be 0 or 1..16.` **포함** | Range 검증이 **거부**한다 |
| 0 제외 중복 | `Non-zero values must be unique.` **포함** | 중복 검증이 **거부**한다 |
| 두 배정 모두 비마방진 | `No magic square completion exists for this input.` **포함** | 조합 시도 후 **차단**, `UI_UNSOLVABLE` |
| 유효 입력 + 해 존재 | 성공 표현(구현 자유) + **계약상** 길이 6·1-index 좌표 | 기본/반대 배정 규칙에 따라 **해를 반환**한다 |
| (선택) 저장/로드 실패 | `Failed to persist or load the matrix.` **포함** | I/O가 **실패**하고 `UI_DATA_ERROR` 매핑 |

**원칙**: “~한다”로 끝나는 **허용/거부/반환/차단**이 Logic에 있고, “보인다/포함한다”가 UI 트랙에 대응한다.

---

## 4. MLOps에 맞춘 정렬(이 PRD를 그 프레임에 올리기)

이 프로젝트는 **학습형 규칙 엔진**이 아니라 **결정적 도메인**이지만, MLOps에서 쓰는 **같은 층**으로 읽으면 정리가 깔끔합니다.

| MLOps 관념 | 이 PRD의 대응 |
|------------|----------------|
| **데이터 계약** | §4.1 입력 스키마, I-01 … I-05 |
| **모델/서빙 출력 계약** | §4.2 성공 출력 `int[6]`, 좌표·`n1,n2` 순서 규칙 |
| **에러 계약(API)** | §4.3 코드·문구·우선순위 |
| **재현성·결정성** | §6.1, NFR — “같은 입력 → 같은 출력”(MLOps의 seed·버전 고정과 같은 역할) |
| **품질 게이트** | §6.2 커버리지 목표(Domain 95%+, UI 85%+, Data 80%+) |
| **아티팩트 불변** | §6.3 변경 금지 — 회귀 보호(스펙 = 릴리즈 가능한 계약) |
| **데이터 파이프라인 실패** | `UI_DATA_ERROR`, 통합 시나리오의 저장/로드 실패(선택) |

즉, **UI 트랙 = 서빙/게이트웨이 계약 테스트**, **Logic 트랙 = 코어 + 검증 파이프라인 테스트**, **MLOps 마인드 = 계약·재현성·게이트·데이터 경로**로 한 줄에 놓을 수 있습니다.

---

## 5. 아키텍처(ECB) — 트랙에 매핑

| 레이어 | Dual-Track |
|--------|------------|
| **boundary** | **UI Track** 주 무대(파싱, 검증 결과 표현, 에러 매핑) |
| **control** | **Logic Track** — 유스케이스 오케스트레이션 |
| **entity** | **Logic Track** — 순수·결정적 마방진 규칙 |

의존성: boundary → control → entity (기존 §7.2).

---

## 6. 사용자 여정 · 스토리 · 검증(기존 내용의 위치만 이동)

- **여정** §3.2: 계약 정의 → Domain 분리 → **Dual-Track 병렬 RED** → 회귀 확장.  
- **스토리 1–5** §8: Story 1(검증)은 **양 트랙**(boundary 메시지 + logic 거부); Story 2–5는 **주로 Logic**, boundary는 최종 포맷만 맞추면 됨.  
- **검증 §9**: 통합 시나리오(정상 2종, 실패 3종+) + **모든 I-xx는 테스트 1개 이상**과 추적.

---

## 7. 가정 · 리스크(기존 §10)

- 가정: 1..16, 빈칸 2개, 2가지 배정으로 스코프 충분.  
- 리스크: 문구·포맷 변경 시 대량 회귀(의도됨), 에러 우선순위 흔들림(테스트로 고정).

## 8. PRD 본문 목차로 쓰고 싶을 때 제안 TOC

1. 제품 개요 · 목표/비목표  
2. **Dual-Track 원리**(독립성 한 줄)  
3. **UI Track — UX Contract & Boundary 요구**  
4. **Logic Track — Logic Rule & Invariants**  
5. **매핑 표**(위 표 확장)  
6. **MLOps 정렬**(데이터·출력·에러 계약, 재현성, 게이트, 변경 금지)  
7. ECB

## 1. 전체 적합도

문서는 **계약 중심 PRD**로 이미 강하고, 컨셉의 핵심인 **“계약을 테스트로 고정”**, **ECB로 경계와 도메인 분리**, **결정성·회귀 보호**가 §1–§7, §6.3에 잘 박혀 있습니다. 다만 **UI 트랙 vs 로직 트랙을 나누는 언어(UX Contract / Logic Rule)**와 **MLOps식 절(데이터·아티팩트·게이트)**은 **명시적 섹션으로는 없고**, 내용이 §3·§4·§8에 **섞여** 있습니다.

## 2. Dual-Track과의 매칭

| 컨셉 요소 | PRD 반영 | 평가 |
|-----------|----------|------|
| 두 트랙 병렬 | §1.2, §3.2 Step 4에 **Dual-Track TDD** 명시 | 명확 |
| UI = Boundary | §7.1 boundary 정의, §6.2 **UI Boundary** 커버리지 목표 | 있음 |
| Logic = Domain | §5 불변식, §8.2–8.5, §6.2 **Domain Logic** | 있음 |
| 트랙 독립 원칙 | “UI 테스트는 Domain…”, “Domain 규칙 테스트” 수준의 문장만 있고, **“UI는 로직을 모른다”** 같은 한 줄 원칙은 없음 | 약함 |
| UX Contract 언어 | “보인다/활성화” 같은 **UI 상태 언어**는 없음. 대신 **에러 `message` 완전 일치**(§4.3)로 boundary 계약이 강하게 고정됨 | 이 프로젝트에는 실용적이나, 슬라이드의 “UX Contract” 프레임과는 표현이 다름 |
| Logic Rule 언어 | I-xx, “거부/반환”은 **암시적**; 동사로 통일된 Logic Rule 목록은 없음 | 약함 |
| 3단 매핑 표 | 없음 | **정리 컨셉 대비 공백** |

정리하면, **의도와 구조는 Dual-Track과 맞고**, **교재·온보딩용으로는 “트랙별 절 + 매핑 표”를 PRD에 한 블록 추가**하면 컨셉과 문서가 1:1로 맞습니다.

## 3. MLOps 정렬 관점

| MLOps에 흔히 쓰는 말 | PRD 대응 |
|----------------------|----------|
| 입력/데이터 계약 | §4.1, I-01–I-05 | 잘 맞음 |
| 출력/서빙 계약 | §4.2 | 잘 맞음 |
| 실패 스키마·코드 | §4.3 | 잘 맞음 |
| 재현성·결정성 | §2.1, §6.1 | 잘 맞음 |
| 품질 게이트 | §6.2 커버리지, 레이어별 목표 | 잘 맞음 |
| “릴리즈 불변” | §6.3 | 잘 맞음 |
| 데이터 경로 실패 | `UI_DATA_ERROR`, §9.1 선택 시나리오 | 있음 |

## 4. ECB와 스토리의 트랙 배정

- **§7**은 boundary / control / entity를 나누어 Dual-Track의 **배치 규칙**과 잘 맞습니다.
- **§8**은 기능 스토리 중심이라, **어느 AC가 주로 UI(boundary) 테스트이고 어느 것이 Logic(entity/control) 테스트인지**는 문서가 구분해 주지 않습니다.  
  - Story 1: **양쪽**(메시지·코드 vs 검증 규칙).  
  - Story 2–4: **주로 Logic**.  
  - Story 5: Logic + **실패 시 `UI_UNSOLVABLE` 표현**은 boundary 쪽과 맞물림.

개선 여지는 **스토리마다 “UI Track AC / Logic Track AC” 한 줄씩**만 붙이는 것입니다.

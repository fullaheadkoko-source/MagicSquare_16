### Level 1: Epic (비즈니스 목표) — EPIC: Business Goal

- **Epic**: “Invariant(불변조건) 기반 사고 훈련 시스템 구축”

- **목적**: 4x4 Magic Square 문제를 활용하여 다음 역량을 체계적으로 훈련한다.  
  - **Invariant 중심 설계 사고 훈련**: 문제를 “조건(불변식) → 규칙 → 검증”으로 구조화하는 사고를 습관화  
  - **Dual-Track TDD 적용 훈련**: Discovery(요구/규칙 발견)와 Delivery(구현/검증)를 분리해 학습  
  - **입력/출력 계약 명확화 훈련**: 경계(Boundary)에서의 스키마/형식 검증과 오류 매핑을 명확히 정의  
  - **설계 → 테스트 → 구현 → 리팩토링 흐름 체화**: Red-Green-Refactor를 “설계 근거(불변식)”와 연결해 반복 학습

- **성공 기준 (Definition of Success)**  
  - **Domain Logic 테스트 커버리지 95% 이상**  
  - **입력 검증 100% 계약(Contract) 테스트 통과**  
  - **하드코딩 없음**  
  - **매직 넘버 없음**  
  - **Invariant → Test 추적 가능** (각 불변식이 어떤 테스트로 검증되는지 명시적으로 연결됨)

### Level 2: User Journey (사용자 여정)

- **Persona**
  - **대상**: 소프트웨어 개발 학습자
  - **상태**: TDD 훈련 중, Clean Architecture 이해 중

- **Journey**

- **Step 1 — 문제 인식**
  - **핵심 전환**: “마방진을 구현한다”가 아니라 **“불변조건(Invariant)을 식별하고 검증 가능한 규칙으로 만든다”**로 문제를 재정의한다.
  - **질문 프롬프트**: “무엇이 항상 참이어야 하는가?”, “무엇이 깨지면 실패인가?”

- **Step 2 — 계약 정의**
  - **입력 스키마 정의**: 4x4 그리드 형식, 허용 값 범위/중복 정책, 빈칸 표현 규칙(예: 2개의 결손) 명시
  - **출력 스키마 정의**: 완성된 4x4 그리드, 채워진 두 값, 성공/실패 상태 구조 명시
  - **예외 정책 정의**: 스키마 오류 vs 도메인 불가능(해 없음/다해) vs 내부 오류를 구분하고, 메시지/코드 매핑 규칙을 확정

- **Step 3 — Domain 분리**
  - **BlankFinder**: “빈칸(결손 위치)” 탐지 책임
  - **MissingNumberFinder**: “누락된 숫자 후보 집합” 계산 책임
  - **MagicSquareValidator**: “마방진 불변식(합/중복/범위 등)” 검증 책임
  - **Solver**: 위 구성요소를 조합해 “해 찾기/해 없음/다해”를 결정하는 책임

- **Step 4 — Dual-Track 진행**
  - **UI RED / Logic RED 병렬**: Boundary 계약 테스트(입출력/오류)와 Domain 규칙 테스트(불변식) 동시 Red
  - **GREEN 최소 구현**: 각 트랙에서 테스트를 통과시키는 최소 구현만 추가
  - **REFACTOR 통합 정리**: ECB 경계 정리, 중복 제거, 이름/책임 조정(동작 변경 없이)

- **Step 5 — 회귀 보호**
  - **엣지 케이스 추가**: 경계값/특수 배치/최소 정보 상황 등
  - **입력 오류 케이스 추가**: 스키마 위반, 범위 위반, 중복, 빈칸 수 불일치 등
  - **조합 실패 케이스 추가**: 해가 없는 경우, 해가 여러 개인 경우(정책에 따른 처리 포함)

### Level 5: 시나리오 검증 및 정리

#### 시나리오 완성도 체크리스트

- ✅ **4레벨 일관성 확인**

- **Epic → Journey**
  - [x] **Epic의 성공 지표가 Journey에 반영됨**  
    - 커버리지(95%+) → Step 5 회귀 보호(엣지/오류/실패 케이스 확장)
    - 입력 계약 100% → Step 2 계약 정의(스키마/예외 정책)
    - 하드코딩/매직 넘버 없음 → Step 3 Domain 분리 + 상수/규칙의 명시화(예: 34, 4, 1~16)
    - Invariant → Test 추적 가능 → Step 1(불변식 식별) ↔ Step 4/5(테스트로 고정)
  - [x] **Journey의 모든 단계가 Epic 목표 달성에 기여**
  - [x] **Pain Points가 명확히 정의됨**
    - “구현부터 시작”하려는 습관
    - 입력 오류가 Domain으로 침투하는 문제
    - 규칙(불변식)과 테스트가 분리되어 추적 불가해지는 문제
    - 조합 실패/다해/해없음 등 실패 모드의 누락

- **Journey → Story**
  - [x] **Journey의 각 Stage마다 최소 1개 Story**
    - Step 2 → Story 1 (입력 검증)
    - Step 3 → Story 2~4 (Blank/Missing/Validator)
    - Step 4 → Story 5 (조합/시도 정책)
    - Step 5 → Story 1~5에 예외/엣지/실패 케이스 확장으로 반영
  - [x] **Story가 구체적인 기능으로 변환됨**
  - [x] **Acceptance Criteria가 측정 가능**

- **Story → Technical**
  - [x] **모든 AC가 Gherkin 시나리오로 변환**
  - [x] **Given-When-Then이 명확**
  - [x] **테스트 자동화 가능**

#### ✅ Edge Case 커버리지

- **정상 케이스**
  - [x] **Happy Path 시나리오 존재** (작은 수→큰 수 / 역순 성공)

- **예외 케이스**
  - [ ] **네트워크 오류** *(해당 과제는 로컬 계산 문제로 네트워크가 스코프 아님 — 제거/비활성화 권장)*
  - [ ] **권한 없음** *(동일 — 제거/비활성화 권장)*
  - [x] **잘못된 입력** (4x4 아님, 빈칸 수 불일치, 중복, 범위 위반)
  - [ ] **중복 실행** *(결정적 순수 계산이라 멱등성으로 해석 가능 — “동일 입력→동일 출력” 테스트로 대체 권장)*

- **경계 케이스**
  - [x] **최솟값, 최댓값** (1, 16 및 0의 위치 조합)
  - [x] **빈 값** *(입력 스키마 관점에서: 누락/None/비정수 등으로 구체화 필요)*
  - [ ] **특수 문자** *(텍스트 입력 파서가 있을 때 boundary 계약 테스트로 의미 있음 — 현재는 숫자 행렬 입력이라 “비정수 토큰” 케이스로 재정의 권장)*

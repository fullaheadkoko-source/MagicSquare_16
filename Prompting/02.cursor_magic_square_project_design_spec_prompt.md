**User**

당신은 Dual-Track UI + Logic TDD 및 Clean Architecture 설계 전문가입니다.

프로젝트: Magic Square (4x4) — TDD 연습용
목적: 알고리즘 난이도보다 “레이어 분리 + 계약 기반 테스트 + 리팩토링” 훈련
제약:
- 구현 코드는 작성하지 마십시오. (설계/계약/테스트/통합 계획만)
- UI는 실제 화면이 아니라 “입력/출력 경계(Boundary)”로 정의
- Data Layer는 DB가 아니라 “저장/로드 인터페이스(메모리/파일 교체 가능)” 수준만
- 입력/출력은 명확히 고정

입력 계약:
- 4x4 int[][] (0은 빈칸)
- 빈칸은 정확히 2개
- 값 범위: 0 또는 1~16
- 0 제외 중복 금지
출력 계약:
- int[6]
- 좌표는 1-index
- 반환 형식: [r1,c1,n1,r2,c2,n2]
- n1,n2는 두 누락 숫자이며, (작은수→첫빈칸, 큰수→둘째빈칸) 조합이 마방진이면 그 순서로, 아니면 반대로

**Cursor**

요구하신 **Dual-Track(UI 계약) + Logic TDD + Clean Architecture** 관점으로, “구현 없이” **도메인/경계/데이터/통합 테스트 설계**를 완성하겠습니다. 먼저 현재 보고서에 이미 정해진 용어/규칙이 있는지 확인한 뒤, 그에 맞춰 계약/테스트/추적표까지 한 번에 정리하겠습니다.

# 1) Logic Layer (Domain Layer) 설계

## 1.1 도메인 개념
- **Entity: `MagicSquare4x4`**
  - **책임(SRP)**: 4x4 격자 상태를 보유하고, “마방진 검증/완성 판정”에 필요한 질의용 정보를 제공한다(행/열/대각선 값 접근, 빈칸 좌표 조회 등).
- **Value Object: `Matrix4x4`**
  - **책임(SRP)**: 입력 `int[][]`를 “정확히 4x4”로 고정된 구조로 캡슐화한다. 인덱싱 규칙(0-index 내부)과 외부 좌표 변환(1-index)과 무관하게 **데이터 자체의 형태 불변**을 보장한다.
- **Value Object: `Cell`**
  - **책임(SRP)**: 좌표(행,열)를 단일 값으로 표현한다. (도메인 내부는 0-index, 외부(UI 출력)는 1-index로 변환)
- **Value Object: `MissingPair`**
  - **책임(SRP)**: 누락 숫자 2개를 “(작은 수, 큰 수)”로 정규화해 보관한다.
- **Value Object: `FillAttempt`**
  - **책임(SRP)**: “두 빈칸 좌표 + (n1,n2) 배정” 한 번의 시도를 표현한다.
- **Domain Service: `InputConstraintValidator`**
  - **책임(SRP)**: “입력 계약 위반”을 판정한다. (크기/빈칸 개수/값 범위/중복)
- **Domain Service: `MissingNumbersFinder`**
  - **책임(SRP)**: 0을 제외한 값 집합(1~16)에서 누락된 2개 숫자를 계산한다.
- **Domain Service: `MagicRuleChecker`**
  - **책임(SRP)**: “마방진 규칙” 검증(행/열/대각선 합 동일)을 수행한다.
- **Domain Service(Orchestrator): `MagicSquareCompletionPolicy`**
  - **책임(SRP)**: 두 빈칸에 (작은수→첫빈칸, 큰수→둘째빈칸) 조합을 먼저 시도하고, 실패 시 반대로 시도한다. 성공 시 최종 출력 순서를 결정한다.

## 1.2 도메인 불변조건(Invariants)
아래 규칙은 **검증 가능(테스트로 Yes/No)** 해야 하며, 위반 시 “도메인 실패(유스케이스 실패)”로 처리한다.

### A. 입력 계약 불변식(Preconditions)
- **I-01 (Shape)**: 입력은 정확히 `4x4`여야 한다. (행 수=4, 각 행의 열 수=4)
- **I-02 (EmptyCount)**: 값 `0`(빈칸)은 정확히 2개여야 한다.
- **I-03 (Range)**: 각 셀 값은 `0` 또는 `1..16` 범위여야 한다.
- **I-04 (UniqNonZero)**: `0`을 제외한 값은 중복이 없어야 한다.
- **I-05 (MissingExactly2)**: `1..16` 중 입력에 없는 값은 정확히 2개여야 한다. (I-02~I-04 충족 시 자동으로 따라오지만, 독립 규칙으로 테스트 가능하게 유지)

### B. 마방진 규칙 불변식(Domain Rules)
- **I-06 (MagicConstant)**: 대상 값 집합이 `1..16`이고 완성된 경우, 마방진 상수는 **34**여야 한다.  
  - 근거: \( \sum_{k=1}^{16} k = 136 \), 행 4개이므로 \( 136/4 = 34 \)
- **I-07 (RowSum)**: 4개 모든 행의 합은 동일해야 한다(완성 상태에서는 34).
- **I-08 (ColSum)**: 4개 모든 열의 합은 동일해야 한다(완성 상태에서는 34).
- **I-09 (DiagSum)**: 2개 대각선 합은 동일해야 한다(완성 상태에서는 34).
- **I-10 (DeterministicOrderRule)**: 출력 `n1,n2` 순서는 “기본(작은→첫빈칸, 큰→둘째빈칸) 배정이 마방진이면 그 순서”이고, 아니면 “반대로”여야 한다. (성공이 없는 경우는 별도 실패)

---

## 1.3 핵심 유스케이스(도메인 관점)
- **UC-01 빈칸 찾기**: `0`인 셀 2개의 좌표를 (스캔 순서 기준) `(firstEmpty, secondEmpty)`로 얻는다.
  - 스캔 순서 규칙(명시): **행 우선, 열 증가**(r=0..3, c=0..3). 첫 번째로 발견된 0이 `firstEmpty`.
- **UC-02 누락 숫자 찾기**: `1..16` 중 입력에 없는 값 2개를 `(smallMissing, largeMissing)`로 얻는다.
- **UC-03 마방진 판정**: 완성된 4x4에 대해 I-06~I-09을 만족하면 true.
- **UC-04 두 조합 시도 및 출력 결정**
  - 시도 1: `firstEmpty=smallMissing`, `secondEmpty=largeMissing`
  - 시도 2(필요 시): `firstEmpty=largeMissing`, `secondEmpty=smallMissing`
  - 성공한 시도의 `(n1,n2)`가 최종 출력에 반영된다.
  - 두 시도 모두 실패면 “해당 입력으로는 마방진 완성이 불가능”으로 실패 처리.

## 1.4 Domain API(내부 계약)
아래는 “메서드 시그니처 수준” 계약이며, 구현 코드는 포함하지 않는다.

### 공통 실패 모델(도메인 내부)
- **`DomainError`**(추상)
  - `InvalidShapeError` (I-01 위반)
  - `InvalidEmptyCountError` (I-02 위반)
  - `OutOfRangeValueError` (I-03 위반)
  - `DuplicateValueError` (I-04 위반)
  - `MissingNumbersNotTwoError` (I-05 위반)
  - `UnsolvableMagicSquareError` (UC-04 두 조합 실패)

### API 목록
- **`Matrix4x4 parse(int[][] raw)`**
  - **입력**: `raw`
  - **출력**: `Matrix4x4`
  - **실패조건**: I-01 위반 시 `InvalidShapeError`
- **`void validateInput(Matrix4x4 matrix)`**
  - **입력**: `matrix`
  - **출력**: 없음
  - **실패조건**: I-02~I-05 위반 시 해당 `DomainError`
- **`Cell[] findEmptyCells(Matrix4x4 matrix)`**
  - **입력**: `matrix`
  - **출력**: 길이 2의 `Cell[]` (정렬 규칙: UC-01 스캔 순서)
  - **실패조건**: I-02 위반이면 `InvalidEmptyCountError`
- **`MissingPair findMissingNumbers(Matrix4x4 matrix)`**
  - **입력**: `matrix`
  - **출력**: `(small, large)`
  - **실패조건**: I-03~I-05 위반이면 해당 에러
- **`boolean isMagicSquare(Matrix4x4 completed)`**
  - **입력**: 빈칸이 없는 `completed`(0이 없어야 함)
  - **출력**: true/false
  - **실패조건**: 0이 있으면 `DomainError`(예: `IncompleteMatrixError`를 추가 정의해도 됨) 또는 false로 규정(둘 중 하나를 고정해야 테스트 가능).  
    - **추천 고정**: “0 존재 시 false”로 단순화(검증 함수는 항상 반환), 완성 요구는 오케스트레이터에서 강제.
- **`int[] completeAndDescribe(int[][] raw)`**
  - **입력**: `raw` (UI/앱 계층이 그대로 전달 가능)
  - **출력**: `int[6]` = `[r1,c1,n1,r2,c2,n2]` (r,c는 1-index)
  - **실패조건**:
    - 입력 계약 위반: 각 `DomainError`
    - 두 조합 모두 마방진 불가: `UnsolvableMagicSquareError`

## 1.5 Domain 단위 테스트 설계(RED 우선)
아래 테스트는 “도메인 레벨”에서 **규칙(I-xx)을 보호**한다. (테스트 이름은 예시이며, Given/When/Then을 고정해 RED부터 시작)

### 정상(성공) 케이스
- **T-D-01 (I-10 보호)**: 기본 배정(작은→첫빈칸, 큰→둘째빈칸)이 마방진이면 출력 `n1<n2`이며 해당 순서로 반환된다.
- **T-D-02 (I-10 보호)**: 기본 배정이 실패하고 반대 배정이 성공하면 출력은 반대 순서로 반환된다(즉, `n1>n2` 가능).
- **T-D-03 (UC-01 보호)**: 빈칸 2개 좌표가 “행 우선/열 증가 스캔” 순서로 반환된다(첫 빈칸/둘째 빈칸 결정 규칙 고정).

### 비정상(입력 계약 위반) 케이스
- **T-D-10 (I-01 보호)**: 4x4가 아닌 입력(행 4 아님) → `InvalidShapeError`
- **T-D-11 (I-01 보호)**: 행은 4개지만 특정 행의 열 수가 4가 아님 → `InvalidShapeError`
- **T-D-12 (I-02 보호)**: 0이 1개 → `InvalidEmptyCountError`
- **T-D-13 (I-02 보호)**: 0이 3개 이상 → `InvalidEmptyCountError`
- **T-D-14 (I-03 보호)**: 값이 -1 포함 → `OutOfRangeValueError`
- **T-D-15 (I-03 보호)**: 값이 17 포함 → `OutOfRangeValueError`
- **T-D-16 (I-04 보호)**: 0 제외 중복(예: 5가 2개) → `DuplicateValueError`

### 비정상(도메인 규칙 실패) 케이스
- **T-D-20 (UC-04 보호)**: 입력 계약은 만족하지만 두 조합 모두 마방진 불가 → `UnsolvableMagicSquareError`

### 엣지(경계) 케이스
- **T-D-30 (I-03 보호)**: 1과 16 포함은 허용(범위 경계값) + 다른 계약 충족 시 검증 통과
- **T-D-31 (I-05 보호)**: 0 두 개가 있어도 실제로 누락 숫자가 2개가 아니게 만드는 입력(중복/범위 오류와 결합)에서 **가장 먼저 위반된 규칙**으로 실패가 결정되는지(에러 우선순위 규칙을 고정)  
  - **에러 우선순위(권장, 테스트로 고정)**: Shape → EmptyCount → Range → Duplicate → MissingNotTwo → Unsolvable

# 2) Screen Layer (UI Layer) 설계 (Boundary Layer)

## 2.1 사용자/호출자 관점 시나리오
- **S-01 정상 흐름**
  - 호출자가 `int[][]`를 입력한다
  - UI Boundary가 입력 계약을 검증한다(형태/빈칸/범위/중복)
  - Domain(유스케이스)을 호출해 `int[6]`를 받는다
  - UI Boundary는 결과를 “지정 포맷”으로 출력한다
- **S-02 오류 흐름**
  - 입력 검증 실패 → Domain 호출 없이 표준 에러를 반환
  - Domain에서 “해 없음” 실패 → 표준 에러를 반환
  - (선택) Data 저장 실패 → 표준 에러를 반환

## 2.2 UI 계약(외부 계약)
UI는 “화면”이 아니라 **입력/출력 경계**다.

### Input schema (고정)
- **`matrix`**: `int[4][4]`
  - 값: `0` 또는 `1..16`
  - 0의 개수: 정확히 2
  - 0 제외 중복 금지

### Output schema (성공 시, 고정)
- **`result`**: `int[6]`
  - `[r1,c1,n1,r2,c2,n2]`
  - `r1,c1,r2,c2`는 **1-index** (1..4)
  - `n1,n2`는 누락 숫자 2개
  - **순서 규칙**: Domain의 I-10을 그대로 따른다(기본 배정 성공이면 그 순서, 아니면 반대)

### Error schema (실패 시, 고정)
- **`error`** 객체:
  - `code`: 문자열(아래 표준 코드 중 하나)
  - `message`: 문자열(아래 표준 문구와 정확히 일치)
  - `details`: 선택(테스트 가능한 고정 필드만 허용. 예: `{ "expected":4, "actualRows":3 }`)

#### 표준 에러 코드/문구(정확 문구 규칙)
| code | message (정확히 일치) | 발생 조건 |
|---|---|---|
| `UI_INVALID_SHAPE` | `Matrix must be 4x4.` | I-01 위반 |
| `UI_INVALID_EMPTY_COUNT` | `Matrix must contain exactly 2 empty cells (0).` | I-02 위반 |
| `UI_OUT_OF_RANGE` | `Cell values must be 0 or 1..16.` | I-03 위반 |
| `UI_DUPLICATE_NON_ZERO` | `Non-zero values must be unique.` | I-04 위반 |
| `UI_UNSOLVABLE` | `No magic square completion exists for this input.` | UC-04 실패 |
| `UI_DATA_ERROR` | `Failed to persist or load the matrix.` | Data 실패(선택) |

**문구 규칙(검증 가능):**
- **E-UX-01**: message는 위 표의 문자열과 **완전 동일**해야 한다(대소문자/마침표 포함).
- **E-UX-02**: 입력 검증 에러는 “첫 위반 1개만” 반환한다(다중 에러 리스트 금지). 에러 우선순위는 Domain 권장 우선순위를 그대로 사용한다.

---

## 2.3 UI 레벨 테스트(Contract-first, RED 우선)
**전제**: Domain은 Mock(스텁)으로 가정한다. UI는 “계약/검증/포맷”만 테스트한다.

### 입력 검증 테스트(요구 항목 포함)
- **T-UI-01**: 크기 오류(행 != 4) → `UI_INVALID_SHAPE` + message 정확히 일치
- **T-UI-02**: 크기 오류(어떤 행의 열 != 4) → `UI_INVALID_SHAPE`
- **T-UI-03**: 빈칸 개수 1개 → `UI_INVALID_EMPTY_COUNT`
- **T-UI-04**: 빈칸 개수 3개 → `UI_INVALID_EMPTY_COUNT`
- **T-UI-05**: 값 범위 오류(-1 또는 17) → `UI_OUT_OF_RANGE`
- **T-UI-06**: 중복 오류(0 제외) → `UI_DUPLICATE_NON_ZERO`

### 반환 포맷 검증 테스트
- **T-UI-10**: Domain이 `int[6]`를 반환하면 UI는 **그대로** `result=int[6]`로 내보낸다(길이 6 고정 확인).
- **T-UI-11**: `r1,c1,r2,c2`는 1..4 범위여야 한다(밖이면 UI는 계약 위반으로 `UI_DATA_ERROR` 또는 `UI_UNSOLVABLE`로 “변환 금지/허용” 중 하나를 고정해야 함).  
  - **추천 고정**: UI는 Domain 결과를 신뢰(도메인 계약)하고, UI에서 좌표 범위 재검증은 하지 않는다. 대신 통합 테스트에서 도메인 결과 계약을 보장.

### 도메인 실패 전달 테스트
- **T-UI-20**: Domain이 “해 없음” 예외/실패를 반환하면 UI는 `UI_UNSOLVABLE` + 표준 message로 매핑한다.
- **T-UI-21**: Domain이 입력 계약 위반을 반환하면 UI는 해당 UI 코드로 1:1 매핑한다(Shape/EmptyCount/Range/Duplicate).

---

## 2.4 UX/출력 규칙
- **UX-01 (단일 결과)**: 성공 시 오직 `result`만 반환하고 `error`는 포함하지 않는다.
- **UX-02 (단일 에러)**: 실패 시 오직 `error`만 반환하고 `result`는 포함하지 않는다.
- **UX-03 (에러 우선순위 고정)**: Shape → EmptyCount → Range → Duplicate → Unsolvable → Data 순으로 첫 위반만 반환한다.
- **UX-04 (문구 고정)**: 2.2 표의 message는 리팩토링/로케일 변경 대상이 아니다(회귀 보호).
- **UX-05 (출력 배열 포맷 고정)**: 성공 결과는 반드시 길이 6의 정수 배열이며, 순서 `[r1,c1,n1,r2,c2,n2]`는 변경 금지.

# 3) Data Layer 설계 (Data Layer)

## 3.1 목적 정의
학습 목적(레이어 분리/계약 기반 테스트)을 위해 Data Layer는 “DB”가 아니라 아래만 담당한다.
- **저장 범위(고정)**:
  - 입력 행렬(`int[4][4]`) 저장/로드
  - (선택) 실행 결과 `int[6]` 저장/로드
- **금지 범위(명확히 제외)**:
  - 도메인 규칙 검증 수행 금지
  - UI 에러 메시지 생성 금지
  - 알고리즘/완성 로직 수행 금지

---

## 3.2 인터페이스 계약
- **`MatrixRepository.saveInput(Matrix4x4 matrix)`**
  - **입력**: 4x4 행렬(도메인 VO)
  - **출력**: 없음
  - **실패조건**: 저장 실패 시 `DataError`(예: `IOException`, `SerializationError`)
- **`MatrixRepository.loadInput()`**
  - **입력**: 없음
  - **출력**: `Matrix4x4`
  - **실패조건**: 파일 없음/읽기 실패/형식 오류 시 `DataError`
- **(선택) `ResultRepository.saveResult(int[6] result)`**
- **(선택) `ResultRepository.loadResult()`**

**Data 불변식(검증 가능):**
- **D-01**: 저장된 행렬은 로드 후에도 “정확히 4x4” 형태가 유지되어야 한다.
- **D-02**: 저장된 값은 로드 후에도 값이 동일해야 한다(정합성).
- **D-03**: 저장 포맷 오류는 “명시적 실패”로 보고해야 한다(조용히 기본값 반환 금지).

---

## 3.3 구현 옵션 비교(메모리/파일)
| 옵션 | 장점 | 단점 | 테스트 포인트 |
|---|---|---|---|
| **A: InMemory** | IO 없음, 빠르고 결정적, 테스트가 단순 | 프로세스 종료 시 소실, 파일 오류 시나리오 학습 불가 | save/load 정합성, 참조 복사(깊은 복사) 여부 |
| **B: File (JSON/CSV)** | “파일 없음/권한/형식 오류” 등 현실적 실패를 학습 가능, 회귀 재현 용이 | IO로 테스트 복잡도 증가, 환경 의존 | 파일 없음, 형식 오류, 라운드트립 |

**추천안: 옵션 B (File-JSON)**  
- **이유(검증 가능)**:
  - 통합 실패 시나리오(데이터 실패)를 실제로 만들 수 있다.
  - 저장된 테스트 픽스처로 회귀 재현이 가능하다(동일 입력 재실행).
  - JSON은 2차원 배열 표현이 명확하고 형식 오류 케이스를 만들기 쉽다.

---

## 3.4 Data 레이어 테스트
- **T-DATA-01 (D-01, D-02)**: `saveInput` 후 `loadInput`이 동일 값/동일 4x4를 반환한다(라운드트립).
- **T-DATA-02 (D-01)**: 로드된 데이터가 4x4가 아니면 `DataError(FormatError)`로 실패한다.
- **T-DATA-03 (D-03)**: 파일이 없으면 `DataError(NotFound)`로 실패한다.
- **T-DATA-04 (D-03)**: JSON 형식이 깨진 파일이면 `DataError(FormatError)`로 실패한다.
- **T-DATA-05 (깊은 복사 규칙)**: `saveInput`에 전달한 매트릭스를 외부에서 변경해도 저장된 결과가 오염되지 않는다(스냅샷 저장 규칙을 고정).

# 4) Integration & Verification (통합 및 검증)

## 4.1 통합 경로 정의
의존성 방향은 **UI → (Application) → Domain → Data(인터페이스)** 이고, 구현 의존은 “안쪽을 향한다”.

- **UI Boundary**
  - 입력 검증(외부 계약)
  - 유스케이스 호출
  - 결과/에러 매핑
- **Application(선택, 권장)**
  - 트랜잭션/흐름 오케스트레이션(저장/로드 포함)
  - Domain 호출 조합
- **Domain**
  - 입력 계약(도메인 관점) + 규칙 + 완성 시도
- **Data**
  - 저장/로드만 담당(규칙 판단 금지)

---

## 4.2 통합 테스트 시나리오
### 정상 시나리오(2개 이상)
- **IT-OK-01**: 유효 입력 + 기본 배정 성공 → UI가 `int[6]` 결과를 정확 포맷으로 반환
- **IT-OK-02**: 유효 입력 + 기본 배정 실패/반대 배정 성공 → UI가 반대 순서의 `n1,n2`를 포함한 `int[6]` 반환

### 실패 시나리오(3개 이상)
- **IT-NG-01 (입력 오류)**: 0이 3개 → UI가 Domain 호출 없이 `UI_INVALID_EMPTY_COUNT`
- **IT-NG-02 (도메인 실패)**: 입력 계약 만족하지만 두 조합 모두 마방진 불가 → `UI_UNSOLVABLE`
- **IT-NG-03 (데이터 실패)**: 저장 옵션을 켠 실행에서 파일 쓰기 실패(권한/경로) → `UI_DATA_ERROR`
- **(선택 추가) IT-NG-04 (데이터 형식 오류)**: 로드 시 JSON 형식 오류 → `UI_DATA_ERROR`

---

## 4.3 회귀 보호 규칙
- **R-01 (테스트 유지 정책)**: 한번 통과한 테스트는 삭제/완화 금지. 변경이 필요하면 “새 계약”을 만들고 신규 테스트를 추가한다.
- **R-02 (계약 변경 금지)**: 입력 계약(4x4, 0=2개, 범위, 중복 금지)과 출력 포맷(`int[6]`, 1-index, 순서 규칙)은 변경 금지.
- **R-03 (에러 문구 변경 금지)**: 2.2의 표준 message 문자열은 변경 금지(문자 1개라도 변경되면 테스트 실패가 정상).
- **R-04 (에러 우선순위 변경 금지)**: UX-03 우선순위는 변경 금지.

---

## 4.4 커버리지 목표
- **Domain Logic**: **95%+**
  - 분기 기준: 입력 계약 위반 분기, 두 조합 시도 분기, 마방진 판정 분기 포함
- **UI Boundary**: **85%+**
  - 계약 검증/에러 매핑/출력 포맷 검증 분기 포함
- **Data**: **80%+**
  - 성공 라운드트립 + 주요 실패(파일 없음/형식 오류) 분기 포함

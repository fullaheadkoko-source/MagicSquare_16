### 문제점 보고

- **1) YAML 문법 오류**
  - 없음. 현재 내용은 YAML로 파싱 가능합니다(빈 섹션들은 `null` 값).

- **2) 누락된 필수 섹션**
  - 없음. 요청하신 최상위 키 9개가 모두 존재합니다(`project`, `code_style`, `architecture`, `tdd_rules`, `testing`, `forbidden`, `file_structure`, `ai_behavior`).

  - 충돌 판단 불가(=명시된 충돌 없음). `forbidden` 섹션이 비어 있어 `tdd_rules`를 제한/위배시키는 규칙이 정의돼 있지 않습니다.

- **4) Cursor AI가 실제로 따를 수 없는 `ai_behavior` 규칙**
  - 해당 없음. `ai_behavior` 섹션이 비어 있어 “따를 수 없는 규칙” 자체가 정의돼 있지 않습니다.

  ECB 패턴 3 레이어를 각각 정의해줘:
  - boundary: 외부 입출력 담당 (UI, API, CLI)
  - control: 비즈니스 로직 담당
  - entity: 도메인 데이터 및 규칙 담당

testing:

  - coverage_minimum: 80%
  - fixture_scope: 규칙 정의
  - naming_convention: test_ 접두사 필수

forbidden:

    - ECB 레이어 경계 위반 금지
    - 타입힌트 없는 함수 생성 금지

**Cursor**

전체 `.cursorrules`를 MagicSquare 프로젝트 기준으로 채우되, 요청하신 스키마(각 섹션별 필수 키/형식)와 기존 80자 구분선 주석은 유지해서 업데이트하겠습니다. 먼저 현재 파일을 기준으로 한 번에 정확히 교체해 반영합니다.

################################################################################
project:
  name: MagicSquare
  domain: 4x4 Magic Square completion (two missing numbers)
  primary_language: python
  goals:
    - Clean ECB layering (boundary/control/entity)
    - TDD-first development with high-quality tests
    - Deterministic behavior and reproducible results
  non_goals:
    - UI styling/visual design (unless explicitly requested)
    - Premature optimization
################################################################################
code_style:
  python_version: "3.10+"
  style_guide: PEP8 엄격 준수
  type_hints: 모든 함수 파라미터와 반환값에 필수
  docstring: Google 스타일, 모든 public 메서드에 필수
  max_line_length: 88
################################################################################
architecture:
  ecb:
    boundary:
      definition: 외부 입출력 담당 (UI, API, CLI)
      responsibilities:
        - 입력 파싱/검증(형식/스키마 수준)
        - 출력 포맷팅 및 에러 매핑
        - 외부 프레임워크/IO에 대한 어댑터
      must_not:
        - 도메인 규칙/알고리즘(마방진 판정/완성) 구현
        - entity 내부 구조에 직접 의존(우회 접근)
    control:
      definition: 비즈니스 로직 담당
      responsibilities:
        - 유스케이스 오케스트레이션(흐름 제어)
        - entity 조합 및 규칙 적용 호출
        - boundary에 반환할 성공/실패 결과 구성
      must_not:
        - 외부 IO(파일/네트워크/콘솔) 직접 수행
    entity:
      definition: 도메인 데이터 및 규칙 담당
      responsibilities:
        - 도메인 불변식 및 규칙(마방진 조건) 보존
        - 도메인 데이터 구조(예: 4x4 매트릭스/좌표/누락값) 표현
        - 순수 함수/결정적 로직 중심
      must_not:
        - 프레임워크 의존/IO/환경 접근
  dependency_direction:
    rule: 바깥에서 안쪽으로만 의존 (boundary -> control -> entity)
    allowed:
      - boundary -> control
      - control -> entity
    forbidden:
      - entity -> control
      - entity -> boundary
      - control -> boundary
################################################################################
tdd_rules:
  red_phase:
    description: 테스트를 먼저 작성하고, 실패를 확인한 뒤에만 다음 단계로 진행한다.
    rules:
      - 새 기능/버그 수정마다 테스트를 먼저 추가한다.
      - 테스트는 의도를 1개만 검증하도록 작게 작성한다.
      - 실패 원인이 명확해야 한다(불안정/랜덤/외부 의존 금지).
    must_not:
      - 테스트 없이 구현 코드를 먼저 작성
      - 실패 확인 없이 바로 green으로 진행
  green_phase:
    description: 테스트를 통과시키는 최소한의 코드만 작성한다(품질 개선은 refactor에서).
    rules:
      - 가장 단순한 구현으로 테스트를 통과시킨다.
      - 통과 후 즉시 다음 테스트 또는 refactor로 전환한다.
      - 불필요한 일반화/추상화는 미룬다.
    must_not:
      - 리팩터링(구조 개선, 함수 분해/이름 변경, 추상화 도입)
      - 성능 최적화/코드 스타일 정리(기능과 무관한 변경)
  refactor_phase:
    description: 기능 변경 없이 구조를 개선하고, 테스트/커버리지를 유지한다.
    rules:
      - 모든 테스트가 통과하는 상태를 유지하며 작은 단위로 변경한다.
      - 중복 제거, 이름 개선, 책임 분리, ECB 경계 정리를 수행한다.
      - 커버리지가 하락하지 않도록 유지한다.
    must_not:
      - 기능/동작 변경(스펙 변경 포함)
      - 테스트 삭제로 커버리지 확보를 회피
################################################################################
testing:
  framework: pytest
  pattern: AAA (Arrange-Act-Assert)
  coverage_minimum: 80%
  fixture_scope:
    rules:
      - 기본은 function 스코프를 사용한다(테스트 독립성 우선).
      - session/module 스코프는 비용이 큰 초기화(예: 대형 픽스처)에서만 예외적으로 사용한다.
      - fixture는 외부 IO에 의존하지 않고 결정적으로 동작해야 한다.
  naming_convention:
    - test_ 접두사 필수
################################################################################
forbidden:
  - pattern: "print(...)"
    reason: "테스트/라이브러리 코드에 부수효과를 만들고 출력이 계약이 되기 쉬움"
    alternative: "logging 모듈 사용 또는 호출자에게 값/에러를 반환(테스트는 반환값/예외를 검증)"
  - pattern: "하드코딩 상수(매직 넘버/매직 스트링)"
    reason: "의미가 불명확하고 변경 시 누락/불일치로 버그가 발생"
    alternative: "의미 있는 상수/Enum/설정값으로 정의(예: MAGIC_CONSTANT=34, SIZE=4)"
  - pattern: "except:"
    reason: "SystemExit/KeyboardInterrupt 등까지 삼켜 디버깅/안정성을 해침"
    alternative: "구체 예외를 명시하고 필요한 경우에만 catch, 재던지기/도메인 에러로 매핑"
################################################################################
file_structure:
  # ECB 기반 폴더 구조 (예시)
  # .
  # ├─ boundary/
  # │  ├─ cli/
  # │  ├─ api/
  # │  └─ ui/
  # ├─ control/
  # │  ├─ use_cases/
  # │  └─ services/
  # ├─ entity/
  # │  ├─ models/
  # │  ├─ rules/
  # │  └─ errors/
  # └─ tests/
  #    ├─ boundary/
  #    ├─ control/
  #    └─ entity/
################################################################################
ai_behavior:
  before_coding:
    - 코드 작성 전 관련 테스트 파일/테스트 케이스를 먼저 확인하고, 없으면 테스트부터 추가한다.
    - 변경 범위가 ECB 레이어 경계를 침범하는지 점검하고, 침범 가능성이 있으면 설계를 먼저 정리한다.
    - 새로 만드는 모든 함수는 타입힌트(파라미터/반환)를 포함해야 한다.
  during_coding:
    - ECB 레이어 경계 위반(예: entity에서 IO/프레임워크 접근, control에서 boundary 의존)을 금지한다.
    - 타입힌트 없는 함수 생성/수정은 금지한다.
    - green_phase에서는 테스트 통과 목적 외의 리팩터링을 하지 않는다.
  after_coding:
    - tdd_rules 위반이 감지되면 경고를 출력한다(예: 테스트 없이 구현, green에서 리팩터링 수행).
    - 최소 단위 변경으로 유지되었는지, 테스트가 해당 변경을 충분히 커버하는지 점검한다.

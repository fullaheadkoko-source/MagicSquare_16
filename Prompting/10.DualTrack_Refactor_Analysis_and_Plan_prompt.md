원하시는 건 **`green` 브랜치 기준으로 새 `refactoring` 브랜치를 만드는 작업**이에요. 먼저 현재 작업 트리 상태와 브랜치 위치를 확인한 뒤, `green`으로 이동해서 그 커밋에서 `refactoring` 브랜치를 생성하겠습니다.

PowerShell에서 `&&`가 파서 에러로 막혀서, 명령을 `;`로 분리해서 다시 확인한 다음 `green` 기준으로 `refactoring` 브랜치를 만들게요.

지금 상태가 깔끔해요(변경사항 없음) 그리고 이미 `green`에 계십니다. 이제 이 커밋을 기준으로 `refactoring` 브랜치를 생성하고 바로 체크아웃까지 진행하겠습니다.

### 완료
- **`green` 기준으로 `refactoring` 브랜치를 생성**했고, 현재 **`refactoring` 브랜치로 체크아웃**되어 있습니다.
- 작업 트리도 **clean** 상태입니다.

## 1) 각 파일이 현재 담당하는 ECB 역할

- **`magicsquare/domain.py` → Control(로직)**
  - 현재 내용은 **상태(데이터)를 “보관”하는 Entity가 아니라**, `matrix`를 입력으로 받아 계산하는 **순수 함수(규칙/계산)** 위주입니다.
  - `find_blank_coords`, `find_not_exist_nums`는 “도메인 규칙 실행” 성격이라 **Control** 쪽에 가깝습니다.

- **`magicsquare/boundary.py` → Boundary 역할은 “부분적으로만” 수행**
  - `validate_4x4_shape()`로 **입력 형태(4x4)** 계약을 강제하는 건 Boundary로 적절합니다.
  - 다만 현재 UI에서 필요로 하는 공개 계약(예: “0은 정확히 2개”, 값 범위, 중복 금지 등)을 **Boundary가 아니라 UI(`app.py`)가 일부 떠안고** 있어 Boundary 역할이 완결적이지는 않습니다.

- **`magicsquare/screen/app.py` → UI 로직 외 책임이 섞여 있음(섞임)**
  - `_on_solve_clicked()` 안에
    - **입력 파싱/정규화(빈 문자열→0)**,
    - **도메인 전제 검증(빈칸 2개, missing 2개)**,
    - **도메인 계산 호출(find_*)**,
    - **도메인 결과를 UI 출력 포맷으로 변환(좌표 1-index, 결과 문장 구성)**
    가 함께 있어, UI(Boundary) 외 책임(Control/변환 로직)이 섞여 있습니다.

## 2) 잘못된 위치의 코드가 있다면, 어디로 이동?

- **`app.py`의 “규칙/검증(빈칸 2개, missing 2개)” → `boundary.py` 또는 `domain.py`**
  - “입력 계약 위반을 UI 에러로 보고 싶다”면 **`boundary.py`** 쪽이 더 ECB에 맞습니다. (Boundary에서 검증하고 `UIBoundaryError`로 통일)
  - “도메인 불변식(항상 2개여야만 의미가 있다)”로 강제하고 싶다면 **`domain.py`**에서도 방어적으로 검증할 수 있지만, ECB 관점에선 **경계에서 먼저 차단**하는 편이 보통 더 깔끔합니다.

- **`app.py`의 “좌표 1-index 변환/결과 메시지 조립” → Control 계층(새 파일) 또는 Boundary 유틸**
  - UI 문자열/표현 포맷은 UI에 남겨도 되지만, “도메인 결과(좌표, 후보값)”를 **UI 표시용 DTO로 변환**하는 로직이 커지면 `magicsquare/control.py`(또는 `service.py`) 같은 **Control 파일**로 빼는 게 리팩토링에 유리합니다.
  - 핵심은 `app.py`는 **입력 수집 + 호출 + 표시**까지만 남기는 방향입니다.

- **`app.py`의 “입력 파싱(빈칸→0, int 변환)” → Boundary 성격**
  - UI 위젯 텍스트를 “도메인 입력 모델”로 바꾸는 단계는 Boundary 쪽 책임에 가깝습니다. (현재는 `app.py`에 있음)

## 3) `domain.py` 안에 Entity와 Control이 혼재한다면, 분리 포인트?

- **현재 `domain.py`는 Entity가 거의 없고 Control 위주라 “혼재”가 크지 않습니다.**
  - `matrix: list[list[int]]`는 **Entity(도메인 모델)** 라기보다 “원시 자료구조”를 그대로 받는 형태입니다.

다만 앞으로 `domain.py`에 아래가 추가되면 **Entity/Control 분리**가 필요해질 가능성이 큽니다.

- **분리 필요 신호(추가/예정 기능 기준)**
  - 보드를 나타내는 불변식(4x4, 값 범위/중복/0개수)을 **데이터 자체가 책임**지게 만들고 싶다면:
    - **Entity 후보**: `Board`(예: `cells`, `blanks`, `missing` 같은 파생값/검증 포함)
  - 보드에 대해 “해결/판정/추천” 같은 동작을 수행한다면:
    - **Control 후보**: `Solver`, `MagicSquareRules`(예: is_magic_square, solution 등)

즉, `domain.py`에 “보관/검증되는 데이터 모델(예: Board)”이 들어오는 순간부터는 **Entity(데이터 모델) 파일과 Control(규칙/해결) 파일을 분리**하는 게 ECB에 더 잘 맞습니다.
